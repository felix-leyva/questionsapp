## Question 1

What is a limitation of UML regarding the Context View?

- [ ] It does not support any behavior diagrams for the context view.
- [x] There is no UML support for structure diagrams in the context view.
- [ ] It only supports the deployment view.
- [ ] It cannot represent external actors.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** UML lacks structure diagram support for Context View. It does support behavior
diagrams (Use Case), supports multiple views (not just deployment), and can represent external
actors—structure diagram gap is the limitation.

</p>
</details>

## Question 2

What are some non-UML alternatives for structure diagrams in the Context View?

- [ ] Class diagrams and sequence diagrams.
- [x] IT landscape and structured interface documentation.
- [ ] Activity diagrams and state diagrams.
- [ ] Deployment diagrams and component diagrams.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Non-UML Context View structure alternatives include IT landscape and interface
documentation. Class/sequence are UML diagrams, activity/state show behavior, and
deployment/component are UML structural diagrams for different views.

</p>
</details>

## Question 3

In the domain view, what documents the domain language, and what is its purpose according to
domain-driven design?

- [ ] Sequence diagrams, to show interactions.
- [x] A glossary, to impose structure on the architecture.
- [ ] Component diagrams, to show static structure.
- [ ] Deployment diagrams, to show physical deployment.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Glossaries document domain language, imposing DDD structure on architecture. Sequence
diagrams show interactions, component diagrams show static structure, and deployment diagrams show
infrastructure—not domain language purposes.

</p>
</details>

## Question 4

What does the "Emergent Domain-Driven Architecture" (EDDA) aim to integrate?

- [ ] Only structural aspects of the architecture.
- [ ] Only behavioral aspects of the architecture.
- [x] Both domain and technical views (like building block and deployment views), as well as
  structural and behavioral aspects, for a consistent representation.
- [ ] Only UML diagrams.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** EDDA integrates domain/technical views (Building Block, Deployment) and
structural/behavioral aspects for consistent multi-perspective representation. Structural-only,
behavioral-only, and UML-only all miss EDDA's comprehensive integration purpose.

</p>
</details>

## Question 5

What are two general views that can be documented with Architectural Decision Records (ADR) and the
ARC 42 standard structure?

- [ ] Only functional requirements.
- [x] Structural and behavioral aspects of software architecture.
- [ ] Only technical implementation details.
- [ ] Only project management timelines.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** ADR and arc42 cover structural and behavioral architectural aspects. Functional
requirements, technical implementation details, and project timelines are separate
concerns—ADR/arc42 address architectural decisions and structure.

</p>
</details>

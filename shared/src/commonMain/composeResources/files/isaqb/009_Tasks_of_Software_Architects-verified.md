## Question 1

According to the text, which of the following are primary tasks of a software architect?

- [x] Constructing and designing components, interfaces, and structures.
- [ ] Implementing detailed business logic in production code.
- [x] Evaluating possible solutions and arguing for them in front of stakeholders.
- [ ] Managing sprint planning and daily standups.
- [x] Documenting architectural decisions.
- [x] Simplifying the complexity of the software project.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Architects design components/interfaces/structures, evaluate solutions, document decisions, and simplify complexity. Implementing detailed business logic is developers' work, and sprint planning is a project management task, not core architectural responsibilities.

</p>
</details>

## Question 3

Which of these pairs represents a conflicting set of quality criteria that a software architect must balance?

- [ ] Performance optimization and fault tolerance mechanisms together.
- [x] Introducing abstractions for flexibility versus maintaining comprehensibility.
- [ ] Satisfying functional requirements and addressing non-functional ones.
- [ ] Time constraints and budget limitations as primary considerations.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Abstractions increase flexibility but reduce comprehensibility—a fundamental architectural trade-off. Performance and fault tolerance can complement each other, functional and non-functional requirements aren't inherently conflicting, and time/budget are project constraints, not architectural quality criteria.

</p>
</details>

## Question 4

What is the recommended relationship between an architect and the development team for the best cooperation?

- [ ] The architect should maintain distance from implementation for perspective.
- [ ] The architect should coordinate exclusively through team leads only.
- [x] The architect should be embedded in the team as a programming architect.
- [ ] The architect should deliver complete specifications before development.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Best cooperation occurs when architects are embedded in the team as programming architects. Maintaining distance, indirect communication, or upfront-only involvement creates disconnects between architecture and implementation reality.

</p>
</details>

## Question 5

Before developing a new system idea, what initial step should an architect take?

- [ ] Build a proof-of-concept prototype to validate initial assumptions.
- [ ] Create comprehensive architectural documentation for stakeholders.
- [x] Research how similar problems were solved using patterns and literature.
- [ ] Conduct a technology evaluation workshop with the development team.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Architects should first research how similar problems were solved elsewhere (past projects, literature, patterns). Prototyping, documentation, and team workshops come later after gathering knowledge from existing solutions.

</p>
</details>

- [x] Clarifying influencing factors and constraints through discussion.

## Question 10

What caution is given regarding new ideas or solutions in software architecture?

- [ ] All innovative solutions should be pursued to gain competitive advantage.
- [x] Be skeptical of solutions that cannot be traced back to known precedents.
- [ ] Prefer completely novel approaches that break from traditional patterns.
- [ ] New architectural styles should replace established patterns when possible.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Be skeptical of solutions with no traceable precedent—often they result from poor research. Innovation for its own sake, breaking from proven patterns, and replacing established approaches without justification all contradict this wisdom-based caution.

</p>
</details>

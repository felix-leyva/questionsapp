## Question 1

According to the definition by Len Bass and his co-authors, what does the structure of a system's
architecture comprise?

- [ ] The programming languages and frameworks utilized.
- [x] Software elements, their externally visible properties, and the relationships among them.
- [ ] The team structure and development process methodology.
- [ ] The project's budget allocation and timeline.
- [ ] The hardware on which the system will run.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Bass defines architecture as software elements, their externally visible properties,
and relationships. Languages/frameworks, team structure, budgets, and hardware are separate concerns
from structural architecture.

</p>
</details>

## Question 2

Which of the following statements is a valid conclusion derived from Len Bass's definition of
software architecture?

- [ ] A system has only one rigidly defined structure.
- [ ] The architecture is a direct code representation, not an abstraction.
- [x] Every system possesses an architecture, regardless of whether it was intentionally planned or
  not.
- [ ] Architectural documentation should only exist at the class level.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Every system has architecture whether planned or not (emergent architecture). Systems
have multiple structures, architecture is an abstraction, and documentation spans multiple levels.

</p>
</details>

## Question 3

What is the central idea behind the definition "Software architecture is the sum of all important
definitions made during the development process"?

- [ ] Architecture is primarily about physical server structure.
- [ ] Only decisions made at project beginning are important.
- [x] Architecture is fundamentally about the significant decisions made, such as choosing a
  framework or programming language.
- [ ] The structure of source code is irrelevant to architecture.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Architecture is fundamentally about important decisions (frameworks, languages)
difficult to reverse. Physical structure, initial-only decisions, and code irrelevance contradict
this definition.

</p>
</details>

## Question 4

What future-oriented aspect does the definition "Software Architecture is a framework for change"
emphasize?

- [ ] That architecture should resist all changes maintaining stability.
- [ ] That future changes are impossible to predict and plan for.
- [x] That a good architecture should be prepared for and able to accommodate likely future changes.
- [ ] That architecture is only relevant for initial development phases.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Good architecture prepares for obvious future changes ("framework for change").
Resisting all change, unpredictability, and initial-only relevance contradict this forward-looking
definition.

</p>
</details>

## Question 5

What is the core of the ISAQB's definition of software architecture?

- [ ] The documentation of every single class and function.
- [ ] The specific choice of database technology.
- [x] The structure of a system, consisting of building blocks, interfaces, and their relationships
  to each other and the environment.
- [ ] The strict adherence to a single communication protocol like asynchronous communication.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** ISAQB core: system structure (building blocks, interfaces, relationships to each
other and environment). Complete documentation, database choice, and protocol adherence are
implementation details, not core architecture.

</p>
</details>

## Question 6

When describing the architecture of a system at the module level, what do "elements," "externally
visible properties," and "relationships" refer to, according to Len Bass's definition?

- [ ] Elements are classes, properties are methods, relationships are inheritance.
- [x] Elements are modules, properties are services offered, relationships are calls from one module
  to another.
- [ ] Elements are functions, properties are return types, relationships are variable assignments.
- [ ] Elements are files, properties are file sizes, relationships are file paths.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** At module level: elements=modules, properties=services offered, relationships=calls
between modules. Classes/methods, functions/types, and files/sizes represent different abstraction
levels.

</p>
</details>

## Question 7

What is a key implication of the definition "Software architecture is the sum of all important
definitions made during the development process"?

- [ ] It means that only the initial design phase is important.
- [x] It suggests that documenting architectural decisions might be more beneficial than documenting
  the structure itself.
- [ ] It implies that source code structure is independent of architectural decisions.
- [ ] It focuses solely on technical aspects, ignoring business decisions.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** This definition implies documenting decisions may be more valuable than documenting
structure (structure results from decisions). Initial-only importance, decision independence, and
technical-only focus contradict this.

</p>
</details>

## Question 8

What is the primary focus of Ayon Woods' definition of software architecture, "Software
Architecture, is the set of decisions which, if made incorrectly, may cause your project to be
canceled"?

- [ ] To emphasize the importance of early project completion.
- [ ] To highlight the need for extensive documentation.
- [x] To underscore the potential negative consequences of poor architectural decisions on project
  success.
- [ ] To promote the use of specific architectural patterns.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Woods' definition emphasizes negative consequences of poor architectural decisions
potentially causing project cancellation. Early completion, extensive documentation, and specific
patterns aren't the focus.

</p>
</details>

## Question 9

According to the ISAQB's definition, what is the scope of software architecture regarding the
system's life cycle?

- [ ] It only provides guidelines for initial analysis and design phases.
- [ ] It is primarily concerned with implementation and testing phases.
- [x] It provides guidelines for the entire system life cycle, from analysis and design to
  implementation, operation, and future development.
- [ ] It focuses exclusively on post-deployment maintenance.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** ISAQB architecture covers entire life cycle: analysis, design, implementation,
operation, and future development. It's not limited to initial phases, implementation/testing, or
post-deployment only.

</p>
</details>

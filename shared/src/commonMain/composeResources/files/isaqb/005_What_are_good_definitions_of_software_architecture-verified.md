## Question 1

According to the definition by Len Bass and his co-authors, what does the structure of a system's architecture comprise?

- [ ] The programming languages, frameworks, and development tools selected.
- [x] Software elements, externally visible properties, and their relationships.
- [ ] The team structure, roles, and development process methodology.
- [ ] The project budget allocation, timeline, and resource planning.
- [ ] The hardware infrastructure and network topology requirements.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Bass defines architecture as software elements, their externally visible properties, and relationships. Languages/frameworks, team structure, budgets, and hardware are separate concerns from structural architecture.

</p>
</details>

## Question 2

Which of the following statements is a valid conclusion derived from Len Bass's definition of software architecture?

- [ ] A system has only one rigidly defined architectural structure.
- [ ] The architecture is a direct code representation, not abstraction.
- [x] Every system possesses architecture, planned or emergent.
- [ ] Architectural documentation should exist only at class level.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Every system has architecture whether planned or not (emergent architecture). Systems have multiple structures, architecture is an abstraction, and documentation spans multiple levels.

</p>
</details>

## Question 3

What is the central idea behind the definition "Software architecture is the sum of all important definitions made during the development process"?

- [ ] Architecture is primarily about physical server structure and deployment.
- [ ] Only decisions made at the project beginning are architecturally relevant.
- [x] Architecture is fundamentally about significant decisions like frameworks.
- [ ] The structure of source code is irrelevant to architectural concerns.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Architecture is fundamentally about important decisions (frameworks, languages) difficult to reverse. Physical structure, initial-only decisions, and code irrelevance contradict this definition.

</p>
</details>

## Question 4

What future-oriented aspect does the definition "Software Architecture is a framework for change" emphasize?

- [ ] That architecture should resist all changes to maintain stability.
- [ ] That future changes are impossible to predict or plan for.
- [x] That good architecture accommodates likely future changes.
- [ ] That architecture is only relevant during initial development.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Good architecture prepares for obvious future changes ("framework for change"). Resisting all change, unpredictability, and initial-only relevance contradict this forward-looking definition.

</p>
</details>

## Question 5

What is the core of the ISAQB's definition of software architecture?

- [ ] The documentation of every single class, function, and method in detail.
- [ ] The specific choice of database technology and persistence mechanisms.
- [x] The structure of building blocks, interfaces, and their relationships.
- [ ] The strict adherence to a single communication protocol throughout.

<details>

## Question 6

When describing the architecture of a system at the module level, what do "elements," "externally visible properties," and "relationships" refer to, according to Len Bass's definition?

- [ ] Elements are classes, properties are methods, relationships are inheritance hierarchies.
- [x] Elements are modules, properties are services offered, relationships are module calls.
- [ ] Elements are functions, properties are return types, relationships are variable assignments.
- [ ] Elements are files, properties are file sizes, relationships are directory file paths.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** At module level: elements=modules, properties=services offered, relationships=calls between modules. Classes/methods, functions/types, and files/sizes represent different abstraction levels.

</p>
</details>

## Question 7

What is a key implication of the definition "Software architecture is the sum of all important definitions made during the development process"?

- [ ] It means that only the initial design phase is architecturally important.
- [x] It suggests documenting decisions may be more valuable than structure.
- [ ] It implies that source code structure is independent of decisions made.
- [ ] It focuses solely on technical aspects and ignores business decisions.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** This definition implies documenting decisions may be more valuable than documenting structure (structure results from decisions). Initial-only importance, decision independence, and technical-only focus contradict this.

</p>
</details>

## Question 8

What is the primary focus of Ayon Woods' definition of software architecture, "Software Architecture, is the set of decisions which, if made incorrectly, may cause your project to be canceled"?

- [ ] To emphasize the importance of early project completion milestones.
- [ ] To highlight the need for extensive documentation throughout.
- [x] To underscore the negative consequences of poor decisions.
- [ ] To promote the use of specific architectural patterns always.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Woods' definition emphasizes negative consequences of poor architectural decisions potentially causing project cancellation. Early completion, extensive documentation, and specific patterns aren't the focus.

</p>
</details>

## Question 9

According to the ISAQB's definition, what is the scope of software architecture regarding the system's life cycle?

- [ ] It only provides guidelines for initial analysis and design phases exclusively.
- [ ] It is primarily concerned with implementation and testing phases only.
- [x] It provides guidelines for the entire system life cycle comprehensively.
- [ ] It focuses exclusively on post-deployment maintenance and operations.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** ISAQB architecture covers entire life cycle: analysis, design, implementation, operation, and future development. It's not limited to initial phases, implementation/testing, or post-deployment only.

</p>
</details>

## Question 1

What is the primary purpose of "Interface Documentation"?

- [ ] To describe internal implementation of building blocks.
- [x] To provide clear description for interface usage.
- [ ] To define programming language for an interface.
- [ ] To manage the deployment of interfaces.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Interface documentation provides clear, precise usage/implementation information. Internal implementation details (separate concern), programming language definition, and deployment management are outside interface documentation scope.

</p>
</details>

## Question 2

Where can interface documentation be located?

- [ ] Only as a standalone document.
- [x] Standalone or as part of other views.
- [ ] Only embedded within the source code.
- [ ] Only in a centralized database.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Interface documentation can be standalone or part of other views (Context View for system embedding). Standalone-only, code-only, and database-only all miss the flexible location options.

</p>
</details>

## Question 3

Which of the following are examples of information that should be included in interface documentation under "Resources, syntax, semantics, restrictions"?

- [ ] The name and version of the interface.
- [x] "Get users" to retrieve user information.
- [ ] Error scenarios like 404.
- [ ] Configuration parameters like max results for pagination.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Resources/syntax/semantics include operations like "Get users" for retrieval. Name/version (metadata section), error scenarios (error handling section), and configuration (configuration section) are separate documentation sections.

</p>
</details>

## Question 4

What kind of information is typically found under the "Quality, service requirements" section of interface documentation?

- [ ] Instructions and examples for usage.
- [x] Non-functional requirements like "99.9% uptime for availability."
- [ ] Design considerations like choosing a RESTful architecture.
- [ ] Error handling procedures.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Quality/service requirements include non-functional requirements like uptime SLAs. Usage instructions, design considerations, and error handling are separate documentation sections.

</p>
</details>

## Question 5

What kind of information is typically found under the "Usage notes, instructions and examples" section of interface documentation?

- [ ] The name and version of the interface.
- [ ] Error scenarios and handling procedures.
- [ ] Design considerations and decisions.
- [x] Instructions and examples for interface usage.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Usage notes/instructions/examples include practical guidance like API key authentication. Name/version (metadata), error scenarios (error handling), and design considerations (design documentation) are separate sections.

</details>

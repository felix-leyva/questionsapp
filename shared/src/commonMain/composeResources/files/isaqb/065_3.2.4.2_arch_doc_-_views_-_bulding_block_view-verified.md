## Question 1

What is the primary purpose of the "Building Block View" in software architecture documentation?

- [ ] To show how the system interacts with external actors only.
- [x] To detail static inner structure: components, subsystems, relationships.
- [ ] To describe the runtime behavior and interactions of the system.
- [ ] To illustrate the deployment of building blocks on physical hardware.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Building Block View details static inner structure—components, subsystems, relationships ("what we think of" for architecture). External actors (Context View), runtime behavior (Runtime View), and deployment (Deployment View) are separate views.

</p>
</details>

## Question 2a

Which architectural abstraction level represents modular units of functionality that can be independently developed and deployed?

- [x] Components
- [ ] External users
- [ ] Network protocols
- [ ] Physical servers

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Components are modular independent units in Building Block View. External users (actors), network protocols (communication mechanisms), and physical servers (infrastructure) aren't functional modularity abstractions.

</p>
</details>

## Question 2b

Which architectural abstraction level represents larger organizational units that group related components together?

- [ ] Classes
- [x] Subsystems
- [ ] Network protocols
- [ ] Virtual machines

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Subsystems are larger organizational units grouping components. Classes are finer-grained, network protocols are communication mechanisms, and VMs are infrastructure, not organizational abstractions.

</p>
</details>

## Question 2c

Which architectural abstraction level represents logical groupings of related classes and interfaces in object-oriented systems?

- [ ] Components
- [ ] External users
- [x] Packages
- [ ] Physical servers

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Packages logically group classes/interfaces in OO systems. Components are coarser-grained, external users are actors, and physical servers are infrastructure, not logical OO groupings.

</p>
</details>

## Question 3

How does the Building Block View help in understanding the source code?

- [ ] By providing a line-by-line explanation of every code file.
- [ ] By automatically generating executable code from the diagrams.
- [x] By allowing understanding at a higher level of abstraction, providing a better overview.
- [ ] By identifying all runtime errors in the code.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Building Block View provides higher-level abstraction and overview. It doesn't explain line-by-line (too detailed), generate code (different purpose), or find runtime errors (testing concern).

</p>
</details>

## Question 6

What kind of relationships between elements are shown in the Building Block View?

- [ ] Only runtime dependencies.
- [x] How the elements are related to each other.
- [ ] Only data flow relationships.
- [ ] Only physical connections.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Building Block View shows how elements relate (dependencies, containment, interfaces). Runtime-only (too narrow), data-flow-only (different concern), and physical-only (Deployment View) all miss static structural relationships.

</p>
</details>

## Question 7

What is the benefit of the Building Block View for understanding the system's source code?

- [ ] It replaces the need to read the source code.
- [x] It allows understanding at a higher level of abstraction, providing a better overview.
- [ ] It automatically generates the source code.
- [ ] It only shows the most complex parts of the code.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Building Block View provides abstraction and overview, complementing code reading. It doesn't replace code reading, generate code, or show only complexity—it clarifies overall structure.

</p>
</details>

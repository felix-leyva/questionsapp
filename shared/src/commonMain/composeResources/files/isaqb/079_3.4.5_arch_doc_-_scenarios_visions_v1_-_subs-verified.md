## Question 1

What is the primary purpose of "Scenarios and Visions" in software architecture documentation?

- [ ] To provide detailed technical specification.
- [x] To tell exemplary business domain stories.
- [ ] To define the programming language to use.
- [ ] To manage project timelines and resources.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Scenarios/visions tell business domain stories in narrative form, describing typical/interesting episodes. Technical specifications, language definitions, and project management are separate concerns outside narrative domain storytelling.

</p>
</details>

## Question 2

How do scenarios and visions facilitate communication between project participants?

- [ ] By eliminating the need for verbal communication.
- [x] By creating discussable precedent cases.
- [ ] By providing a rigid set of rules for interaction.
- [ ] By automating the entire communication process.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Scenarios/visions create discussable precedent cases, facilitating clarification of unclear aspects and unknown terms. Communication elimination, rigid rules, and automation all contradict scenarios' collaborative discussion-enabling purpose.

</p>
</details>

## Question 3

What is the difference between scenarios that depict the "current situation" and those that describe a "desired situation"?

- [ ] Scenarios of current situation are more detailed.
- [x] Current describes work context; visions show usage.
- [ ] Current is for developers; visions are for users.
- [ ] There is no difference; terms are the same.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Current-situation scenarios describe existing work context/processes; visions illustrate desired system usage in known/imaginary contexts. Detail level, stakeholder restrictions, and interchangeability all miss the current vs. desired temporal distinction.

</p>
</details>

## Question 4

What is an "open design scenario" and what is its purpose?

- [ ] A scenario left incomplete for future development.
- [x] A vision using imaginary context for creativity.
- [ ] A scenario open to stakeholder interpretation.
- [ ] A scenario with no predefined context.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Open design scenarios use imaginary contexts to unleash creativity for new solutions. Incomplete scenarios, interpretative openness, and context absence all miss the intentional creativity-unleashing through imaginary context exploration.

</p>
</details>

## Question 5

How do scenarios contribute to modern collaborative modeling methods like domain storytelling?

- [ ] They replace the need for such methods.
- [x] They form the foundation for domain understanding.
- [ ] They are only used for formal documentation.
- [ ] They are irrelevant for collaborative modeling.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Scenarios form the foundation for domain understanding and tailored software development in collaborative methods like domain storytelling. Replacement, formal-only use, and irrelevance all miss scenarios' foundational role in collaborative modeling.

</p>
</details>

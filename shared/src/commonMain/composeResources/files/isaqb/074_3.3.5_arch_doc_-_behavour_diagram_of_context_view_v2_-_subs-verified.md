## Question 1

What is the primary purpose of "Use Case Diagrams" in the context view?

- [ ] To show the internal structure of the system.
- [x] To depict actor and use case relationships.
- [ ] To illustrate deployment of software components.
- [ ] To model dynamic behavior of objects at runtime.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Use Case diagrams depict actor-use case relationships, documenting user goals and interactions. Internal structure (Class diagrams), deployment (Deployment diagrams), and runtime object behavior (Sequence/State diagrams) are separate UML purposes.

</p>
</details>

## Question 2

How can "Use Cases" be managed in a Use Case Diagram?

- [ ] They must always be kept as single, atomic units.
- [x] They can be decomposed into smaller ones, extended, and generalized.
- [ ] They can only be extended, not decomposed.
- [ ] They are static and cannot be changed once defined.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Use cases can be decomposed (smaller units), extended (add functionality), and generalized (abstract common behavior). Atomic-only, extension-only, and static all miss use case modeling flexibility for managing complexity.

</p>
</details>

## Question 3

What is the utility of "Use Case Diagrams" for requirements gathering and communication?

- [ ] They are used for technical implementation details.
- [x] They gather and communicate requirements effectively.
- [ ] They are only useful for very small systems.
- [ ] They replace the need for other documentation.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Use Case diagrams excel at requirements gathering, communication, and functionality breakdown. Technical details, small-system-only limitations, and documentation replacement all miss their requirements-level communication purpose.

</p>
</details>

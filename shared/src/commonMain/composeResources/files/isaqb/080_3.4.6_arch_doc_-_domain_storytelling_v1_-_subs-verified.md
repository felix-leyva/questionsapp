## Question 1

What is "Domain Storytelling" as a collaborative modeling method?

- [ ] A method for writing technical documentation for developers.
- [x] A method for narrating scenarios collaboratively with domain experts and other stakeholders,
  visualizing individual steps.
- [ ] A technique for automating software development.
- [ ] A way to generate code from natural language descriptions.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Domain Storytelling collaboratively narrates scenarios with domain
experts/stakeholders, visualizing individual steps. Technical documentation, automation, and code
generation are separate concerns outside collaborative scenario visualization.

</p>
</details>

## Question 2

What question does a domain story aim to answer?

- [ ] How much does the project cost?
- [x] Who does what with which work objects?
- [ ] What programming language should be used?
- [ ] When will the project be completed?

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Domain stories answer "who does what with which work objects"—focusing on actors,
activities, and domain objects. Cost, programming language, and timeline are project management
concerns, not domain process understanding.

</p>
</details>

## Question 3

In the example of guiding container ships, what is the role of the "sounding team"?

- [ ] To pilot the container ships.
- [x] To measure depths and calculate depth lines to create a sounding plan.
- [ ] To find specific routes for container ships.
- [ ] To contact the captain for a route.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Sounding teams measure depths, calculate depth lines, and create sounding plans.
Piloting, route finding, and captain contact are nautical officer roles, not sounding team
responsibilities.

</p>
</details>

## Question 4

How does the nautical officer find a suitable route for a container ship?

- [ ] By randomly selecting a route.
- [x] By putting the ship silhouette on the sounding plan, shifting and rotating it to simulate
  concrete maneuvers.
- [ ] By consulting a pre-defined database of routes.
- [ ] By asking the captain for their preferred route.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Nautical officers simulate maneuvers by manipulating ship silhouettes on sounding
plans to find suitable routes. Random selection, database consultation, and captain preference all
miss the manual simulation process.

</p>
</details>

## Question 5

What is the benefit of breaking down the domain into subdomains based on process segments?

- [ ] It makes the domain more complex.
- [x] It allows for understanding how these subdomains interact and how they can be separated,
  serving as a blueprint for architecture design.
- [ ] It eliminates the need for any further analysis.
- [ ] It forces all subdomains to be implemented by the same team.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Subdomain breakdown (divide and conquer) enables interaction understanding and
separation, providing architecture blueprints. Complexity increase, analysis elimination, and team
forcing all miss subdomain topology's architecture design benefit.

</p>
</details>

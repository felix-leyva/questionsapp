## Question 1

What is the primary purpose of "Object Diagrams" in the runtime view?

- [ ] To show the static type structure of an OO system.
- [x] To represent class instances as runtime snapshots.
- [ ] To depict internal class structure and collaborations.
- [ ] To illustrate deployment of software on hardware.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Object diagrams show class instances as runtime snapshots, revealing runtime object structures. Static type structure (Class diagrams), class internals (Composite Structure diagrams), and deployment (Deployment diagrams) are separate purposes.

</p>
</details>

## Question 2

Why can "Object Diagrams" sometimes appear simpler than their corresponding "Class Diagrams"?

- [ ] They do not show any relationships between objects.
- [x] They show only concrete objects, not hierarchies.
- [ ] They are only used for very small systems.
- [ ] They do not represent actual class instances.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Object diagrams appear simpler showing only concrete objects, omitting inheritance hierarchies and abstract interfaces. They do show relationships, work for all system sizes, and specifically represent class instances.

</p>
</details>

## Question 3

What is the purpose of "Composite Structure Diagrams"?

- [ ] To show dynamic behavior of a system over time.
- [x] To depict internal class structure and collaborations.
- [ ] To represent object states and transitions.
- [ ] To illustrate control flow between activities.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Composite Structure diagrams depict class internal structure and collaboration possibilities for detailed design. Dynamic behavior (Sequence diagrams), state transitions (State diagrams), and activity flow (Activity diagrams) are separate UML purposes.

</p>
</details>

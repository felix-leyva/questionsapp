## Question 1

What are the key requirements for good architecture documentation?

- [ ] It must be as long as possible to cover all implementation details comprehensively.
- [x] It must be system-specific, accurate, consistent, appropriate, maintainable, and understandable.
- [ ] It must be written by a single architect to ensure consistency throughout.
- [ ] It must only contain technical details without business context or rationale.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Good documentation is system-specific, accurate/consistent, appropriate, maintainable/efficient, target-tailored, and understandable. Length maximization, single authorship, and technical-only content all contradict effective documentation principles.

</p>
</details>

## Question 2

What is the advice regarding the use of templates in architecture documentation?

- [ ] Templates should be avoided to allow for maximum flexibility in documentation style.
- [x] Use templates when helpful for views, interface descriptions, and context differentiation.
- [ ] Templates are only suitable for very small projects with limited complexity.
- [ ] Templates should be used primarily to hide complex implementation details.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Use templates when helpful for views (Context, Building Block, Runtime, Deployment), interface descriptions, and context differentiation. Template avoidance, small-project-only, and complexity hiding all miss templates' structural consistency benefits.

</p>
</details>

## Question 3

What is the advice regarding architectural decisions in documentation?

- [ ] Architectural decisions should not be documented to avoid confusion.
- [x] Document and communicate them with dependencies and justification.
- [ ] Only document the final decision without the alternatives considered.
- [ ] Architectural decisions are only relevant for the initial design phase.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Document and communicate decisions with dependencies and justifications. Non-documentation, final-only recording, and initial-phase-only relevance all miss decisions' ongoing importance and context needs.

</p>
</details>

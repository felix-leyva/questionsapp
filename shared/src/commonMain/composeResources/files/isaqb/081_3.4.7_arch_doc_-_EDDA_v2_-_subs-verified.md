## Question 1

What does EDDA stand for, and what is its purpose?

- [ ] Enterprise Data-Driven Architecture; manage datasets.
- [x] Emergent Domain-Driven Architecture; gradual DDD.
- [ ] Event-Driven Design Analysis; analyze events.
- [ ] Extended Deployment Diagram Analysis; visualize.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** EDDA (Emergent Domain-Driven Architecture) supports gradual DDD architecture development. Enterprise data management, event flow analysis, and deployment visualization are separate architectural concerns outside EDDA's DDD focus.

</p>
</details>

## Question 3

How does the interconnection of sub-domains arise in an EDDA diagram?

- [ ] From random connections between components.

- [ ] From the organizational structure of the development team.

<details>

## Question 4

What is the significance of the "subdomain topology" in EDDA?

- [ ] It is only for visual representation.

- [ ] It dictates the programming languages used.
- [ ] It replaces the need for tech architecture.

<details>

## Question 5

What is the difference in approach to aligning technical architecture with subdomain structure between a Greenfield project and a Brownfield project?

- [ ] In both, exact alignment is always preferred.
- [x] Greenfield prefers exact; Brownfield aims close.
- [ ] Greenfield not needed; Brownfield crucial.
- [ ] In both, alignment is impossible.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Greenfield prefers exact alignment (no legacy constraints); Brownfield aims for closest possible alignment (legacy constraints). Both-exact, greenfield-unnecessary, and both-impossible all miss the greenfield flexibility vs. brownfield constraint distinction.

</p>
</details>

## Question 1

What is the primary purpose of a "Class Diagram" in the building block view?

- [ ] To show the dynamic interactions between objects at runtime.
- [x] To represent the static type structure of an object-oriented system, including classes,
  interfaces, and their relationships.
- [ ] To organize system elements into cohesive groups at a high level of abstraction.
- [ ] To depict the deployment of software components on hardware.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Class diagrams represent static type structure—classes, interfaces, relationships (
composition, aggregation, inheritance). Dynamic interactions (Sequence diagrams), high-level
grouping (Package diagrams), and deployment (Deployment diagrams) are separate diagram purposes.

</p>
</details>

## Question 2

How do "Package Diagrams" contribute to managing large code bases?

- [ ] By showing the detailed internal logic of each class.
- [x] By organizing system elements into cohesive groups to reduce complexity and depict a more
  abstract structure.
- [ ] By illustrating the flow of control between different components.
- [ ] By providing a visual representation of the system's performance metrics.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Package diagrams organize elements into cohesive groups, reducing complexity through
abstraction. Detailed class logic (Class diagrams), control flow (Activity/Sequence diagrams), and
performance metrics (separate concern) aren't packaging purposes.

</p>
</details>

## Question 3

What level of abstraction do "Component Diagrams" provide compared to Package Diagrams?

- [ ] A lower level of abstraction, showing more detail.
- [x] An even higher level of abstraction, presenting a black box or white box view of components
  and their wiring.
- [ ] The same level of abstraction, but with different symbols.
- [ ] Component diagrams are not related to package diagrams.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Component diagrams provide higher abstraction than packages, showing black/white box
component wiring. Lower detail, same level, and unrelated all contradict the abstraction hierarchy:
Class < Package < Component.

</p>
</details>

## Question 4

How can Class, Package, and Component diagrams be integrated with each other?

- [ ] They cannot be integrated; each diagram type is independent.
- [ ] They are integrated by showing only the most abstract level in all diagrams.
- [x] Classes can contain packages, which can have nested sub-packages, and packages can bundle
  classes related to other classes, allowing for different levels of detail.
- [ ] Integration is achieved by converting all diagrams into a single, unified format.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Diagrams integrate through hierarchical containment—classes contain packages,
packages nest sub-packages and bundle related classes. Independence, abstract-only, and
single-format conversion all miss hierarchical integration flexibility.

</p>
</details>

## Question 5

If classes from Component 1 depend on classes from Component 2, but not vice-versa, what does this
imply about the dependency between the components?

- [ ] The components are independent and have no dependency.
- [ ] The dependency flows from Component 2 to Component 1.
- [x] The dependency between components also flows in the same direction, from Component 1 to
  Component 2.
- [ ] This scenario is not possible in a well-designed architecture.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Class-level dependencies aggregate to component-level dependencies in same
direction (Component 1 → Component 2). Independence, reverse flow, and impossibility all miss
dependency propagation from finer to coarser granularity.

</p>
</details>

## Question 6

What kind of relationships are typically shown in a Class Diagram?

- [ ] Only inheritance relationships.
- [x] Complex relationships such as composition, aggregation, and inheritance.
- [ ] Only associations between classes.
- [ ] Only dependencies between packages.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Class diagrams show complex relationships—composition, aggregation, inheritance, plus
associations. Inheritance-only, association-only, and package dependencies (Package diagrams) all
miss Class diagram relationship richness.

</p>
</details>

## Question 7

What is the primary purpose of a "Package Diagram"?

- [ ] To show the dynamic behavior of a system.
- [x] To organize system elements into cohesive groups to reduce complexity and depict a more
  abstract structure.
- [ ] To represent the static type structure of an object-oriented system.
- [ ] To illustrate the deployment of software components.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Package diagrams organize elements into cohesive groups for complexity reduction.
Dynamic behavior (Behavior diagrams), type structure (Class diagrams), and deployment (Deployment
diagrams) are separate UML purposes.

</p>
</details>

What is the primary purpose of a "Component Diagram"?

- [ ] To show the internal details of classes.
- [x] To present a black box or white box view of components and how they are wired together.
- [ ] To organize system elements into packages.
- [ ] To illustrate the dynamic interactions between objects.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Component diagrams present black/white box component views and wiring. Class internal
details (Class diagrams), package organization (Package diagrams), and dynamic interactions (
Behavior diagrams) are separate diagram purposes.

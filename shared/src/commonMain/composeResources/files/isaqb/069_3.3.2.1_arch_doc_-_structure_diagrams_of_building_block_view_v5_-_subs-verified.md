## Question 1

What is the primary purpose of a "Class Diagram" in the building block view?

- [ ] To show dynamic interactions between objects at runtime.
- [x] To represent static type structure with classes and interfaces.
- [ ] To organize system elements into cohesive groups.
- [ ] To depict deployment of software components on hardware.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Class diagrams represent static type structure—classes, interfaces, relationships (composition, aggregation, inheritance). Dynamic interactions (Sequence diagrams), high-level grouping (Package diagrams), and deployment (Deployment diagrams) are separate diagram purposes.

</p>
</details>

## Question 2

How do "Package Diagrams" contribute to managing large code bases?

- [ ] By showing the detailed internal logic of each class.
- [x] By organizing elements into groups to reduce complexity.
- [ ] By illustrating control flow between different components.
- [ ] By providing visual representation of performance metrics.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Package diagrams organize elements into cohesive groups, reducing complexity through abstraction. Detailed class logic (Class diagrams), control flow (Activity/Sequence diagrams), and performance metrics (separate concern) aren't packaging purposes.

</p>
</details>

## Question 3

What level of abstraction do "Component Diagrams" provide compared to Package Diagrams?

- [ ] A lower level of abstraction, showing more detail.
- [x] Higher abstraction with black/white box component views.
- [ ] The same level of abstraction with different symbols.
- [ ] Component diagrams are not related to packages.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Component diagrams provide higher abstraction than packages, showing black/white box component wiring. Lower detail, same level, and unrelated all contradict the abstraction hierarchy: Class < Package < Component.

</p>
</details>

## Question 4

How can Class, Package, and Component diagrams be integrated with each other?

- [ ] They cannot be integrated; each diagram type is independent.
- [ ] They are integrated by showing only most abstract levels.
- [x] Through hierarchical containment with nested packages.
- [ ] By converting all diagrams into a single unified format.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Diagrams integrate through hierarchical containment—classes contain packages, packages nest sub-packages and bundle related classes. Independence, abstract-only, and single-format conversion all miss hierarchical integration flexibility.

</p>
</details>

## Question 5

If classes from Component 1 depend on classes from Component 2, but not vice-versa, what does this imply about the dependency between the components?

- [ ] The components are independent with no dependency.
- [ ] The dependency flows from Component 2 to Component 1.
- [x] Dependency flows same direction: Component 1 to 2.
- [ ] This scenario is not possible in good architecture.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Class-level dependencies aggregate to component-level dependencies in same direction (Component 1 → Component 2). Independence, reverse flow, and impossibility all miss dependency propagation from finer to coarser granularity.

</p>
</details>

## Question 6

What kind of relationships are typically shown in a Class Diagram?

- [ ] Only inheritance relationships.
- [x] Composition, aggregation, and inheritance.
- [ ] Only associations between classes.
- [ ] Only dependencies between packages.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Class diagrams show complex relationships—composition, aggregation, inheritance, plus associations. Inheritance-only, association-only, and package dependencies (Package diagrams) all miss Class diagram relationship richness.

</p>
</details>

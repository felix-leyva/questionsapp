## Question 1

What is the primary purpose of "Sequence Diagrams" in the runtime view?

- [ ] To show the static structure of a system.
- [x] To show time-sequenced object interactions.
- [ ] To depict the internal structure of a class.
- [ ] To illustrate deployment of software components.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Sequence diagrams show time-sequenced object interactions for use case modeling. Static structure (Class diagrams), class internals (Composite Structure), and deployment (Deployment diagrams) are separate UML diagram purposes.

</p>
</details>

## Question 2

What do "Communication Diagrams" focus on?

- [ ] The chronological order of events.
- [x] Object interactions and message organization.
- [ ] The states of an object over its lifetime.
- [ ] The flow of control in a business process.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Communication diagrams focus on object interactions and structural message organization. Chronological order (Sequence diagrams), object states (State diagrams), and process flow (Activity diagrams) are separate behavioral modeling concerns.

</p>
</details>

## Question 3

What is the purpose of "Interaction Overview Diagrams"?

- [ ] To show simple, linear interactions.
- [x] To combine activity and sequence for control flow.
- [ ] To depict static relationships between classes.
- [ ] To illustrate deployment of software on hardware.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Interaction Overview diagrams combine Activity and Sequence elements for complex interaction control flow. Simple interactions, static relationships (Class diagrams), and deployment (Deployment diagrams) are separate concerns.

</p>
</details>

## Question 4

What is a common drawback of Sequence Diagrams, despite their utility?

- [ ] They are too simple to convey meaningful info.
- [x] They quickly become complex with limited scope.
- [ ] They show static relationships, not dynamic behavior.
- [ ] They are rarely used in practice today.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Sequence diagrams quickly become complex, limiting use case portions and object numbers. They're not too simple, do show dynamic behavior (not static), and are widely used—complexity is the limitation.

</p>
</details>

## Question 5

In a Sequence Diagram, how are method invocations and returns typically represented?

- [ ] Both are represented by dashed arrows.
- [x] Solid arrows for invocations, dashed for returns.
- [ ] Both are represented by solid arrows.
- [ ] Dashed arrows for invocations, solid for returns.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Sequence diagrams use solid arrows for method invocations and dashed arrows for returns. Both-dashed, both-solid, and reversed conventions all violate standard UML sequence diagram notation.

</p>
</details>

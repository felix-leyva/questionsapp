## Question 1

What is the primary focus of the "Context View" in architecture documentation?

- [ ] The internal implementation details of the system.
- [x] How the system is embedded in its context, appearing as a black box, and highlighting external
  interactions.
- [ ] The detailed design of individual components within the system.
- [ ] The performance metrics of the system's internal processes.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Context View focuses on external embedding as a black box, highlighting external
actor interactions. Internal details (Building Block View), component design (detailed Building
Block), and performance metrics (Runtime View) are separate architectural concerns.

</p>
</details>

## Question 2

Which types of interfaces are typically considered in the Context View?

- [ ] Only programmatic APIs.
- [x] Web UI, technical API, batch process, and exchange file.
- [ ] Only user interfaces.
- [ ] Only database connections.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Context View considers diverse interface types: Web UI, APIs, batch processes,
exchange files. API-only, UI-only, and database-only all miss the breadth of external interaction
types the Context View documents.

</p>
</details>

## Question 3

Why are key use cases often included as part of the Context View?

- [ ] To provide a detailed step-by-step guide for users.
- [ ] To replace the need for any other documentation.
- [x] To help understand how the system fits into its context.
- [ ] To define the internal algorithms of the system.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Key use cases help understand system context fit. They're not detailed user guides,
don't replace other documentation (Context is just entry point), and don't define internal
algorithms (implementation concern).

</p>
</details>

## Question 4

What is the typical role of the Context View in architecture documentation?

- [ ] It provides a highly detailed technical specification.
- [ ] It is only used by developers for implementation.
- [x] It serves as an entry point, providing a rough overview of the architecture.
- [ ] It is the final and most comprehensive document.

<details>
<summary>Rationale</summary>
<p>

## Question 5

What is the primary characteristic of the system in the Context View?

- [ ] It is shown with all its internal components.
- [x] It appears as a black box, highlighting its external interactions.
- [ ] It is depicted as a white box, showing all its internal logic.
- [ ] It is represented as a single, isolated entity.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** System appears as black box emphasizing external interactions. Internal components (

View's external focus.

</p>

## Question 6

Which type of external actors represent people who interact with the system in the Context View?

- [ ] System administrators only.
- [x] Human users.
- [ ] External developers.
- [ ] Database administrators only.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Human users are the people actors in Context View. Admin-only and DBA-only are too
narrow (missing end users), and external developers aren't typically primary actors.

</p>
</details>

## Question 6a

What category of external actors consists of other software applications or services in the Context
View?

- [ ] Internal modules.
- [x] External systems.
- [ ] Human users.
- [ ] Development tools.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** External systems are other software/services in Context View. Internal modules aren't
external actors, human users are people (not systems), and development tools aren't runtime actors.

</p>
</details>

---

## Question 6b

Which type of external actors represent physical devices or equipment that interact with the system
in the Context View?

- [ ] Virtual machines.
- [ ] Software containers.
- [x] External hardware.
- [ ] Cloud services.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** External hardware represents physical devices/equipment. VMs and containers are
virtualization (not hardware actors), and cloud services are external systems (not hardware).

</p>
</details>

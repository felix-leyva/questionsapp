## Question 1

What is the primary purpose of a "Glossary" in the context of software architecture documentation?

- [ ] To list all technical terms used in the project.
- [x] To document the vocabulary of the domain language and make it accessible to everyone.
- [ ] To define programming language syntax.
- [ ] To track changes in the codebase.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Glossaries document domain language vocabulary, making it accessible to all
stakeholders. Technical term lists, programming syntax, and codebase tracking are separate
documentation purposes outside domain language documentation scope.

</p>
</details>

## Question 2

According to domain-driven design, how does the domain language influence software architecture?

- [ ] It has no influence; architecture is purely technical.
- [x] It directly reflects the terms, structures, and semantics of the business domain, shaping the
  software architecture.
- [ ] It only affects the user interface design.
- [ ] It is only used for communication between developers.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** DDD domain language shapes software architecture, reflecting business domain
terms/structures/semantics. Pure technical architecture, UI-only impact, and developer-only
communication all miss DDD's architecture-shaping principle.

</p>
</details>

## Question 3

Why is it important to define and explain relevant terms in a glossary, especially when dealing with
different domains or synonyms?

- [ ] To make the glossary as long as possible.
- [x] Because even if terms are the same, their meaning can differ across domains, and synonyms or
  new conceptions exist within the same domain.
- [ ] To ensure that only technical experts can understand the documentation.
- [ ] To prevent any new terms from being introduced.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Terms require definition because meanings differ across domains and
synonyms/generalizations exist within domains. Length maximization, expert-only understanding, and
term prevention all contradict glossaries' clarification purpose.

</p>
</details>

## Question 4

What is the advice regarding generalizations in the domain language?

- [ ] Generalizations should be avoided entirely.
- [x] They must make sense to the domain experts.
- [ ] They should only be created by technical architects.
- [ ] They are only for internal documentation.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Generalizations must make sense to domain experts (DDD principle). Complete
avoidance, architect-only creation, and internal-only use all miss domain experts' central role in
validating domain language.

</p>
</details>

## Question 5

Besides vocabulary, what is needed to truly master a language, as suggested by the text?

- [ ] Reading a dictionary.
- [x] Speaking the language, for example, by telling stories in that language.
- [ ] Memorizing all grammatical rules.
- [ ] Translating it into another language.

<details>
<summary>Rationale</summary>
<p>

**Rationale:** Language mastery requires speaking it (telling stories). Dictionaries, grammar
memorization, and translation are tools, not mastery—active use through storytelling demonstrates
true language command.

</p>
</details>
